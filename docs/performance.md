# 性能设计与验收

本文记录 QuizDock 性能专项版本的优化原则、可复现基线与验收标准。所有数据都应注明环境，避免把本机延迟误当成公网体验。

## 用户关键路径

性能优化按用户可感知程度排序：

1. 打开应用并看到可操作的首页。
2. 点击“开始练习”并看到当前题。
3. 切换到下一题或题号导航指定的题目。
4. 提交答案并显示结果。
5. 大题库下滚动、选择选项和展开答题进度。

## v0.3.0 设计约束

- 首屏使用 `/api/v1/bootstrap` 合并认证状态与授权后的元数据，避免两个串行请求。
- 练习启动只将当前题作为阻塞内容；后续 5 题通过 `/api/v1/questions/batch` 在后台预取。
- 预取题目保存在容量受限的内存缓存中，不写入持久化存储；预取失败时切题自动回退为单题请求。
- 批量题目详情无论包含几道题，都只执行题目、Tag、题目组成三组查询，禁止引入 N+1 查询。
- 答题响应直接携带最新学习统计，不允许每答一题重新加载完整题库元数据。
- 题号导航每页最多渲染 160 个按钮；Markdown 输入不变时复用解析结果。
- 学习进度采用短暂防抖写入，页面退出时使用 `keepalive` 刷新最后一条进度。
- 随机队列单独保存一次，滚动位置快照不得重复序列化整条随机队列。

## 2026-09-11 本机基线

测试环境为 2,325 道可练题的正式题库、生产构建、宿主机回环网络。网络延迟未包含在以下数据中。

| 项目 | v0.2.2 | v0.3.0-dev 首轮 |
| --- | ---: | ---: |
| 练习启动响应（gzip） | 约 9–12 ms / 13.4 KB | 约 11 ms / 13.4 KB |
| 连续加载 5 道题 | 5 次请求，合计约 4.5 ms | 1 次请求，平均约 0.9 ms |
| 每次答题后的完整元数据请求 | 1 次，约 14.6 ms | 0 次 |
| 首屏认证与元数据 | 2 次串行请求 | 1 次合并请求 |
| 题号按钮 DOM 数量 | 2,325 | 160 |

生产构建的本机页面加载测量：TTFB 约 0.3 ms、FCP 约 112 ms、LCP 约 148 ms、CLS 为 0。公网部署验收应重点比较请求数量和端到端耗时，而不是直接套用本机毫秒数。

## 发布前验收

```bash
make check
docker build --build-arg VERSION=0.3.0 -t quizdock:0.3.0 .
```

随后使用包含千题以上题库的生产构建验证：

- 首页 Network 面板没有串行的 `auth/status` 与 `meta` 请求。
- 进入练习后出现一条 `practice/start` 和一条后台 `questions/batch`。
- 正常下一题不出现阻塞的 `GET /questions/:uid`；断网或预取失败后恢复网络仍可回退加载。
- 连续快速切题不会被较早响应覆盖，也不会丢失最后练习位置。
- 提交答案只请求 `answers`，不会附带一次完整 `meta` 请求。
- PC 与移动端均无题目、选项或操作按钮被答题进度遮挡。
